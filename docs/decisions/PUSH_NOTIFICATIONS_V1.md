# push通知の保存・監視・配送

2026-10-08。採用。旧コマンドの機能を、共通Outboxと共有公開データ取得へ移植する。

旧版は予約・イベントそれぞれにJSON保存、定期実行、LINE送信、再試行を持っていた。新版では予約を未来期限のActionへ直接保存する。既存next_actionのTimerが起こすため、他の受信・コマンドに依存せず、専用の1秒予約pollingも不要になる。

イベント・ガチャは更新される予定から通知を作る必要があるため、既存run_store_monitorsの取消・寿命にpush_loopを追加する。素材・SKD・gatya/sale/itemと同じHTTP Client・同時2枠・15秒・4MiBを使う。監視は共通Sourceを再利用し、OC数に応じて公開データの取得回数を増やさない。LINEの通知受信を追加pollingする実装ではない。

公開データは登録がある種類だけ取得し、成功後60秒で更新、失敗後も60秒待つ。保持は成功から最大120秒。期限を超えたデータでは新しい通知予定を作らず、既に確定したActionの通常配送は進める。監視のDB確認は5秒ごと、1分先までの通知を事前にActionへ渡す。これにより公開データの取得待ちと期限送信を分ける。一方、既に作った1分先の予定は、その後の公開データ変更を即時には反映しない。

SQLiteの確定済み走査位置はトークごとに保存する。1回の展開は最大5分の時刻範囲、1周期64トーク・新規Action64件まで。未走査分は次周期に進める。容量不足時は該当トークの位置を進めず、既にActionへ渡した同じ時刻・通知種別を重複印で除外して続行する。展開する開催候補・通知行は各最大4,096、本文は通常1,500 UTF-16単位に分割し最大32件、daily本文も最大32件。枠を超える場合はstderrに理由を残し、無制限にメモリやQueueを増やさない。

設定は全体2,048、1トーク128、通知先512トーク。これは対応数の実測保証ではなく有限な保存上限。重複印は32,768件を上限とし、各トークの走査位置より古く、期限から2分過ぎたものを清掃する。未完了の範囲の印は消さない。共通Outboxは全機能合計2,048、PrepareMediaとスレッド親は後続の予約枠も数える。

長期予約の未解決メッセージは最大1,024件とし、予約だけで全Outbox枠を占有させない。予約のAction IDで通知種別を識別し、event_idには元の受信IDを維持する。これにより、未完了の予約がある間は既存の受信ID清掃から保護され、古いコマンドの再取得でも二重登録しない。

停止中は予定を作らず走査位置を現在へ進める。予約・イベント通知は取り出し時も停止を確認する。配送は既存sending/unknown契約を維持し、成否不明のLINE送信を自動で再実行しない。dailyは通常の親投稿が確定してから既存スレッド処理へ進め、本文は1秒待つ。

通常再起動の継続と、遠隔退避の復元は区別する。バックアップ間隔内の変更・送信と、公開予定から消えた過去イベントは完全に復元できない。長時間停止後は現在の公開予定から復元可能な範囲を有限に追跡する。無制限の過去通知保証やAPI制限が絶対に発生しないという保証にはしない。

入力・関数・旧版との差は [pushの実装資料](../../crates/kbc-core/src/push/docs/PUSH.md)、受信・有限並列の既存契約は [PUSHと並列制御](PUSH_AND_BOUNDED_CONCURRENCY_V1.md)に従う。
