# PUSHを基本にし、独立した処理を有限並列にする

決定日: 2026-10-02（JST）
状態: 採用。最小Botへ実装・オフライン検証済み。実LINEのPUSH比較は未実施。現行の境界と制約は[Adapter実装](../../apps/line/docs/ADAPTER.md)を参照。

## 1. 問題と決定

0.2コア・512MBで多数のOCを扱うため、空の定期取得と不要なトーク巡回を減らす。利用者の指定により、基本の受信方式をLINEJSのOC PUSHにする。受信・Command・返信・予定通知を一つの直列な待ち列へまとめず、依存する操作だけ順序を守り、独立した処理は上限付きで並列に進める。

PUSH後にも `fetchMyEvents` 等の取得が必要。直列化の単位は「同じ受信cursorを進める処理」で、Bot全体・全OC・全APIではない。

## 2. 直列と並列の境界

| 対象 | 方針 | 理由 |
| --- | --- | --- |
| アカウント全体の `fetchMyEvents` | 同じアカウント・cursor系統は同時1取得。ページ継続と受付確認もその系統で順に進める | 同じ位置からの競合取得と、応答順によるcursor上書きを防ぐ |
| `fetchSquareChatEvents` | 同じトーク / threadのcursor系統は直列。独立した系統は共通API上限内で並列 | 一つのトークの遅延が別トークの補完を独占しない |
| 正規化・永続受付 | 有限Batchを保存して受付確認。Command完了を待たない | 取得済みEventと対応checkpointを整合して残す |
| Command / 業務処理 | 有限Workerで独立したトークを並列。共有状態や対話に依存する入力は順序を守る | 遅いCommandで別OCの処理・受信を塞がない |
| 返信・予定通知・照会 | 共通ApiSchedulerの有限枠で並列。依存する宛先操作は順序を守る | 通知と応答を自律的に進め、遅い通信の影響を限定する |
| PUSH接続・ACK | 接続管理で扱い、常時接続が短時間RPCの枠を占有しない | 長く開いた接続を理由に配送枠が空かなくなる事態を防ぐ |

短時間RPCの全体上限はまず2並列を初期案とする。同じcursorの1取得もこの上限の内数で、受信・送信・追加照会・SDK内部RPCを別々に2並列ずつ走らせる指定ではない。実装時に設定化し、待ち時間・API種別別回数・制限応答・CPU・Memoryを見て調整する。これはLINEが許容する制限値を表す数ではない。

並列数だけではAPI回数を制御できない。開始間隔、予算、cooldownも共通Schedulerで管理する。実通信の取消・完了を確認してから枠を返し、結果不明の送信を単純に再投稿しない。受信・配送・背景処理の待ち時間を観測し、一つの優先度が他を無期限に占有しない選択規則をBで定義する。

現在の低CPU値は受信Probeのみの実測。Rust Core・Command・保存・返信を含む完成形の余裕はまだ測定していない。通信待ちの並列化は進めつつ、CPU処理のWorker上限は別に管理する。

## 3. 通知を詰まらせない受付と起床

- PUSHは取得を起こす合図として集約する。同じcursor系統へ通知ごとの無制限Taskを作らない。
- 取得中の通知は再取得が必要な状態として残す。Batchの受付確認・継続ページ処理後に再確認し、別の通知やCommandが来るまで待たない。
- 全ページを扱い、有限Inboxへの永続受付後に対応checkpointを確定する。SDK内部の先行cursorとPUSH ACKを永続受付完了として扱わない。
- Coreは通知期限で起床し、ApiSchedulerはenqueue・通信完了・再開・cooldown終了で起床する。予定通知の配送をLINEからの次の入力へ依存させない。
- Buffer・Queue・同時処理数・待機時間は有限にする。容量超過や長い通信を観測し、抑制・取消・再開を定義する。

## 4. 補助取得と復旧

全体通知で不足する参加退出等は、必要な機能とトークを限定して補助取得する。通知されたトークへの取得を集約するが、全体通知自体が来ない場合に備え、設定対象の期限付き補助取得も残す。システムメッセージONがPUSHの発生に影響するかは未確認なので、ONを配信保証として要求しない。

起動・再接続時は永続checkpointから追い付き、IDで重複照合する。購読の異常・初期化失敗・取消を接続管理で扱い、全体取得とトーク別取得のcheckpointを混ぜない。OC専用の購読対象とhandlerを明示し、SDK内部のkeepalive / 認証通信も観測する。復旧・補助取得の周期や再試行はBで定義し、全OCの固定高頻度巡回を既定値として持ち込まない。

SDK既定PUSHループには、[認証なしProbe](../../experiments/linejs-receiver/docs/RECEIVER_PROBE.md)でBuffer引継ぎ・継続ページ・cursor競合等の問題を観測した。PUSHという方式を採用することと、そのループを無変更で本運用することは別の判断。最新版の再確認後、Adapterでの補完・SDK変更の範囲をBで決め、必要な対策だけを実装する。

## 5. 理由・負担・再検討条件

利点は無通信時の空取得削減、固定周期の待機削減、独立したトークの応答・通知を並行して進められること。負担はPUSH購読と再接続の管理、依存関係を守るScheduler、有限Bufferとcheckpointの管理が必要なこと。API制限回避・全件受信・負荷改善は、設計方針の採用だけで実証済みとはしない。

まずPUSHを基準として必要な対策を確認する。採用Runtimeで受信・復旧が成立しない、必要なイベントを保持期間内に回収できない、資源上限を満たせない場合は、原因・測定・代案を示して方式を再検討する。既存の直列取得Probeは比較基準として残す。

## 7. 投稿を起点にしない補助取得（2026-10-03）

本運用で、参加から後続投稿まで通知が届かなかったとの報告を受け、トークイベントを独立取得する。通知設定・参加監視対象3秒、その他60秒を目安とし、PUSH補完と同一cursor・全体2取得・全API2並列/250msを共有する。accountを高頻度巡回しない。API数増加と未発見トークの最大10分待ちを負担として受け入れ、遅れ・制限応答を計測して見直す。[関数・上限・障害時動作](../../apps/line/docs/ADAPTER.md)。

2026-10-04の追記: 一覧の全ページ取得が成功した場合、未参加の旧設定トークは定期取得から外す。設定は消さず、一覧失敗では対象を維持する。未参加先への不要なAPI要求を減らす一方、再参加の発見は次の10分更新を待つ場合がある。PUSH要求による補完は継続する。

## 8. 履歴削除と通常照会（2026-10-08）

alltalkで過去履歴を取得中、!pingだけ応答し他OCのコマンドが止まるとの報告を受けた。実装上、履歴の後続読み取りが元コマンドの古いdueを引き継ぎ、単一照会Workerで新しい通常照会より先に選ばれ続ける問題を確認。履歴・一覧のPurgeは現在dueで登録し、期限到来した通常照会を優先する。共通照会Workerは2本へ増やし、全API2並列・250msは維持する。同じPurgeのcursorは結果保存後に一つずつ進める。負担は通常照会が続く場合のPurge遅延で、従来10分上限を維持する。!bot statusは保存済み状態だけで通常配送へ登録する。[実装と停止操作](../../crates/kbc-core/src/oc/docs/REMOTE_MUTE.md)。実LINEでの詰まり改善は配備後の確認が必要。
