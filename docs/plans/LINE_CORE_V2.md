# KBC LINE Bot Rust Core V2 計画

作成日: 2026-10-01、更新日: 2026-10-02（JST）
状態: PUSH基盤とtxt / ut / tut / stの実装・オフライン検証済み。第一段階全体は未完了。詳細仕様・原因・性能基準は観測で確定する。

## 1. 第一段階の目的

0.2コア・512MBの環境で、多数のOpenChatのイベントを安定して受信し、メッセージを取りこぼさず、API制限を避けられる負荷制御を持つ基盤を作る。

利用者から報告された次の問題を、第一段階の主要な回帰条件とする。

1. コマンド処理後に通知が詰まり、別のコマンドを実行すると送られる。
2. ほぼ同時に2件以上のメッセージを送ると、一方が反応しない。
3. API制限と思われる状態が時々発生する。
4. 応答時間が長く、常時CPU使用率も高い。

受信から通知・返信完了までを一つの経路として確認する。単に処理をRustへ移したことや、接続のheartbeatだけで目標達成とは扱わない。

## 3. 初期構成の提案

```text
apps/line/              TypeScriptのLINEJS Adapter
crates/kbc-protocol/     LINE用のversion付きEvent / Action
crates/kbc-core/         Runtime、受信Inbox、Command、各Service
crates/kbc-node/         薄いN-API Bridge
docs/                   計画、設計判断、調査、運用
```

Discordと同じ3 crate構成とN-APIを第一候補にする。CoreとProtocolからNode.js / LINEJSへ依存しない。TypeScriptを推奨する理由は旧版との仕様照合とRustから生成する型の利用がしやすいため。

N-APIは構成が少ないが、Nativeの致命的障害はNodeと同じプロセスへ影響する。障害隔離に必要性が確認された場合だけ別プロセス構成と比較する。詳細は[構成案](../architecture/CORE_AND_ADAPTER.md)を参照する。

### LINEJSの採用方針

利用者の指定により、最新公開版を使う。2026-10-01にJSRと開発元Releaseを確認し、現時点の基準版を `3.4.2` とする。実装開始時と依存更新時に最新公開版を再確認し、packageとlockには具体的なversionを残す。

`3.3.3` の通信timeout・LEGY取消、`3.4.1` の受信中エラー・初期化失敗の改善を活用する。旧 `3.1.4` 向けパッチは一括で移植せず、最新公開版に統合された修正と、なお再現確認が必要な対策を分ける。[改善点と残る検証](../research/RECEIVER_AND_BACKGROUND_EXPERIMENTS.md#8-最新公開版の改善と採用方針)を参照する。

最新版への更新だけで、同時Commandの無反応、通知停滞、API制限が解消したとは扱わない。最新版で受信・永続受付・配送・負荷制御を一つの経路として確認する。実験フォルダに最新依存を導入し、認証なし検証と旧アカウントでの受信のみの短時間実測を実施済み。配送・負荷制御の実証は残る。

## 4. 第一段階で設計する経路

### 受信を確実に受付へ渡す

```text
LINEのイベント取得
→ 軽量な正規化
→ 有限な永続Inboxへ受付、対応するcheckpointを保存
→ 受信カーソルを進める
→ OCごとの順序と公平性を保って処理
→ CoreAction
→ 共通API実行
→ 結果の記録
```

- 受信側で名前照会・モデレーション・Command完了を待たない。
- 受信APIが返した全ページを扱い、cursor / continuation / subscriptionの意味を採用版で確認する。
- 別message IDの2件を、同じ本文・時刻・送信者という理由だけでまとめない。
- 重複排除はアカウント・トーク・message ID・イベントの意味に基づく。複数経路で同じメッセージを受けた場合も照合する。
- 起動前の作成時刻だけで未処理メッセージを捨てない。再取得イベントの「既処理」と「未処理」を分ける。
- Inboxとcheckpointの整合性、再起動復元、容量超過時の受信抑制を先に設計する。
- 永続Inboxは今回の取りこぼし対策に必要な保存だけを持つ。全メッセージ履歴の常駐索引とは分ける。

保存方式はPhase 0で比較する。イベントとcheckpointを同一transactionで保存できる小さなSQLiteを第一候補に、ファイル形式での整合性・復旧コストと比較する。既存の機能データを一括でSQLiteへ移す計画ではない。

### 通知とAPI待機を自律的に進める

- 通知の期限、実行枠が空く時刻、API cooldown終了を自分のTimerで検知する。
- 別Commandの実行がなければ配送が進まない構成にしない。
- 配送中に追加された仕事・起床要求も完了後に再確認する。
- 終わらない通信と「実行中」の状態を観測し、通知1件で他OCを無期限に塞がない。
- 送信成功、確定失敗、結果不明を分け、結果不明の送信を自動で重複実行しない。

### 全APIの負荷を把握・制御する

送信・削除だけでなく、受信、メンバー・名前照会、参加退出補助監視、履歴、プロフィール更新、SDK内部の再試行も調査する。

アカウント全体の予算と必要なAPI種別・OC別の制御を共通化する。固定の50ms送信間隔を守るだけで制限を防げるとは考えない。LINEJS内部の制限とLINEサーバーからの制限を区別する。

- 受信の進行を背景巡回・一斉通知が塞がないようにする。
- 不要なOC別ポーリングを減らす。 `fetchMyEvents` で十分なイベントと、補助取得が必要なものを実データで分ける。
- 同じ情報の重複照会をまとめ、有限Cacheや未対応APIの負Cacheを使う。
- 全OCのタイマー・通知を同時に発火させず、許容遅延内で分散する。
- 制限応答時は新規要求を抑え、明示された待機時間があれば尊重する。短い固定間隔で再試行しない。
- LINEJSの採用版を固定し、SDKの保護機構・実通信の取消・再試行をコードで確認する。
- 制限の数値が不明な箇所を推測で保証せず、観測した負荷と安全な設定を記録する。

## 7. 測定と第一段階の受入条件

応答を「LINE側の作成 → Adapter受信 → 永続受付 → Command開始・完了 → API実行開始 → 送信完了」に分解する。プロセス内は単調時計、外部時刻との差は時計ずれを含む参考値とする。

| 確認条件 | 判定・観測 |
| --- | --- |
| 同一OC・複数OCで2件以上を同時入力 | 各message IDの取得・受付・処理・結果が追跡でき、対象の全件に応答する |
| Command完了後は何も入力しない | 期限付き通知と待機Actionが自律的に配送される |
| 同じ取得ページの再受信・途中再起動 | 未処理が再開され、既処理を不必要に再実行しない |
| API制限・遅い通信を模擬 | cooldownが効き、再試行の連鎖や全OCの無期限停止を起こさない |
| OC数・イベント量・通知先数を段階的に増加 | API種別別の件数、待機、制限、受信lag、p50 / p95を記録 |
| 無通信・通常利用・背景処理併用 | 常時CPU、throttling、Memory、Timer起床、空取得を比較 |

受信した新着イベントのsilent dropを0件にすることを検証の基本条件とする。「API未取得」「意図した対象外」「取得済みだが未処理」「処理済みだが送信待ち」を区別する。

LINE側の保持期間・再取得能力、切断時間、許容負荷をPhase 0で確認し、取りこぼし防止を確認できた条件を明記する。サーバー側の非公開上限や結果不明の外部操作まで、無条件の完全配送保証にはしない。

CPUは使用core数と0.2コア割当比、Memoryはcgroup current / working set・RSS・Node heap・externalを記録する。旧版と新版は同じ資源・データ量・OC数・測定時間で比較する。同じアカウントの二重ログインで比較しない。

OC数は利用者の指定により段階的に増やして測定し、確認できた範囲を記録する。評価するイベント量、通知の許容遅延、測定期間、CPUと応答の数値目標はPhase 0で確定する。計画時点で根拠のないAPI上限やミリ秒を決めない。

## 8. 検証と残る判断

恒久テストはProtocolのSmokeと実際に報告された重大回帰を中心に、少数のイベント再生・仮想時刻による確認を選ぶ。型・Compilerが保証する単純変換を重複テストしない。本番APIへ大量送信して限界を探ることから始めず、まずオフライン再生と少数OCで確認する。

Phase 0で残る判断:

1. 最新公開版を基準にした受信方式、subscription / cursor / continuation、取消・SDK制限の実挙動。採用方針は確定し、配布物・Runtimeでの検証は残る。
2. 停滞と無反応の再現条件、必要なログ、実際のエラーcodeと制限のscope。
3. 永続Inboxの形式・保持上限・checkpoint・処理済み判定・過負荷時の再取得。
4. API予算、受信と返信・通知・補助監視の優先度・公平性。
5. 対象OC数と入力・通知負荷、通知遅延、観測期間、性能の受入基準。
6. 初期移植subcommand、機能データの正本・保存形式・復元順。
7. 切断、制限、終了時の未処理と結果不明Actionの再開・照合。

各Phaseは「旧コード・一次資料確認 → 原因と仮説の区別 → 方針とトレードオフ → 最小実装 → 最小検証 → 差分とdocs確認」で進める。

## 10. 直近の着手順

最新3.4.2配布物でAの認証なし検証を完了し、既存Northflankサービスと旧Botアカウントで、取得後1秒待機の短時間実測・連続入力・返信有効起動を確認した。[実験結果と切戻し](../../experiments/linejs-receiver/docs/LIVE_CONTAINER_PROBE.md)を記録し、元の停止 0 / 0・Default configurationへ戻した。実LINEの全件照合・実返信は未評価。重なった入力の返信抜けを再現する手動試験は利用者指定で運用観測へ回す。

2026-10-02にB/Cの最小経路を実装。3 crate・型生成・Native、SQLiteの受信/Action/checkpoint同時保存、PUSH起点・ページ継続・指定chat補完、全RPC共通2枠、ping・期限通知を接続した。[Runtime](../../crates/kbc-core/docs/RUNTIME.md)と[Adapter](../../apps/line/docs/ADAPTER.md)に関数・上限・制約を記録。オフラインSmokeでID重複・rollback・再開・自律期限・実SDK Thrift初期応答・継続PUSH集約を確認した。次はDの少数OC確認で、先に[認証とコンテナ保存の扱い](../operations/MINIMAL_BOT.md)を確定する。一般Command Worker・旧権限/停止・thread・全機能移植・本運用負荷は未完了。

| C: 最小経路の実装（Phase 1〜2） | 3 crateとTS Adapter、Protocol型生成、受付・Worker・共通API経路。最小ping応答と期限付き通知を接続 | オフライン再生で同時入力を全件処理し、入力が途絶えても通知が進む。再起動で受付済みの未処理が再開される |
| D: 少数OCでの確認（Phase 2） | 一つの接続で受信・配送を観測し、API種別別回数、応答、無通信CPU、Memoryを記録 | オフライン条件を実LINEでも照合し、OC数・負荷を増やす基準と停止・復旧条件がある |

### Aで先に確認する条件

| 条件 | 確認点 |
| --- | --- |
| 同一OC・複数OCの同時入力 | 本文・時刻が同じでも、異なるmessage IDをそれぞれ受付・追跡する |
| 100件超の取得ページと200件超のStream待機 | 全ページの扱い、Bufferの実際の有限性、consumerの遅延と抑制を確認する |
| Streamのrenew / cancelと受信中のエラー | 新旧Streamの扱いと再取得地点を確認。未処理のIDを黙って捨てない |
| 初期化失敗と遅い通信 | 次のlistenを開始でき、取消・timeout後に実通信と実行枠が解放される |
| SDK内部通信・APIエラー | RPCとPUSHの通信方式を保ちながら観測できるか、再試行・制限がどの経路で起きるか確認する |

最初は認証なしのSDK単体検証とイベント再生を使う。100件超の取得はSDK / 受信層へ模擬ページを返す形で確認し、実LINEの保持・再取得仕様を証明した結果とは分ける。実LINEでなければ判定できない項目は条件付きの未確認として残し、Dで確認する。

API制限の内部値を推測で決めず、まず全通信の観測点を確保する。custom fetchの導入でSDK標準のHTTP/2 PUSHを失わないよう、[通信の接点に関する注意](../research/RECEIVER_AND_BACKGROUND_EXPERIMENTS.md#9-api観測と制御を入れる接点)を確認する。

[PUSH受信の範囲](../research/PUSH_RECEPTION.md)をBの入力にする。PUSH通知後にもAPI取得が必要で、参加者の詳細などが全体取得へ必ず届くとは確認できていない。PUSHの起点を変えるだけで網羅性が改善したとは扱わず、必要なトーク別取得・期限付き補完の条件を設計する。

### BからCへ進む基準

Bでは、取得Batchを原子的に保存してから受付確認を返すことと、未処理Eventを再開できることを最優先にする。SQLite候補は有限なInboxとcheckpointの保存に限定し、依存・I/O・容量管理の負担を比較して採否を記録する。

CのProtocol Smokeは受信受付からAction・結果までを通す1本を基本にし、同時入力・通知の自律配送・途中再起動を少数の重大回帰条件としてまとめる。機能ごとに新しいQueueやTimer基盤を作らない。旧Commandの詳細調査と移植は、計画した対象Phaseの開始前に行う。
